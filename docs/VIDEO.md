# 업로드 영상 분산 처리

메인 화면에서 방을 만들고 MP4·MOV·WebM을 업로드한다. 브라우저 참여자들이 원본 프레임을 가져가 노이즈 제거, 선명도, 밝기·대비·채도를 계산하고 처리한 RGBA를 돌려준다. 고정된 시연 장면을 재생하는 방식이 아니다. 서버는 원본 디코딩·크기/프레임 속도 정규화·최종 H.264 인코딩과 오디오 조립을 담당한다. 참여 브라우저의 WebGPU compute shader가 영상 필터를 계산한다.

## 처리 흐름

1. 방장 권한으로 파일을 스트리밍 업로드한다. 서버가 형식과 길이·해상도를 검사하고 RGBA 원본 프레임과 오디오를 준비한다.
2. 방장은 고정된 필터의 매개변수를 선택해 작업을 시작한다. 참여 동의가 없으면 프레임을 배정하지 않는다.
3. 참여 기기가 작업을 요청하면 독립 프레임 하나와 attempt ID, 만료 시간을 받는다. 활성 작업과 동의를 확인한 뒤 해당 원본 프레임만 내려준다.
4. 기기 안에서는 CPU Workers와 GPU가 행 구간을 나눈다. CPU는 최대 16행, GPU는 최대 64행씩 계산한다. 다음 프레임도 같은 GPU 장치·파이프라인을 재사용한다.
5. 서버는 길이·작업 ID·attempt·권한과 원본 기반 표본 픽셀을 검사한다. 승인한 결과를 디스크에 저장한다. 전 프레임이 모이면 오디오와 함께 MP4를 만든다.

빠른 참여 기기는 다음 프레임을 먼저 요청하므로 더 많은 프레임을 맡는다. 하드웨어 성능을 추정한 고정 비율 분배가 아닌 실제 완료 속도에 따른 pull 방식이다. 프레임이 독립적이므로 이탈 시 해당 프레임만 재배정한다.

## 실제 GPU 연산

`video-gpu.ts`가 고성능 어댑터를 요청하고 하드웨어 여부를 확인한다. [WebGPU 사양](https://gpuweb.github.io/gpuweb/)의 `GPUAdapterInfo.isFallbackAdapter`를 우선 사용하며 소프트웨어 어댑터를 GPU 처리로 표시하지 않는다. 지원 환경은 HTTPS 또는 localhost의 보안 컨텍스트, WebGPU 지원 브라우저와 드라이버다. GPU 확인은 어댑터 조회이고 연산 참여 전에는 GPU 장치·compute 작업을 만들지 않는다.

`video-filter-v1`은 경계를 보존하는 공간 노이즈 제거, 별도 3×3 Gaussian 커널의 디테일 선명화, 밝기·대비·채도 순으로 계산한다. 모든 중간값과 반올림을 정수로 정의해 CPU와 WGSL이 동일한 RGBA를 낸다. 구형 레이트레이서와 달리 GPU 계산 이후 CPU 픽셀 보정이 없다. AI 노이즈 제거, 프레임 사이 정보를 사용하는 시간축 보정, 업스케일 모델은 포함하지 않는다.

GPU 장치 이름, GPU가 계산한 행과 프레임, dispatch 횟수가 실제 Worker 결과에서 갱신된다. `timestamp-query`를 지원하면 GPU 명령 실행 시간도 측정한다. 처리·대기·전송을 포함한 경과 시간, GPU timestamp, OS GPU 사용률은 서로 다른 값이다. 이 앱은 OS 전체 GPU 사용률을 측정하거나 특정 사용률을 보장하지 않는다. 작은 영상에서는 GPU가 일을 짧게 끝내므로 작업 관리자의 평균 사용률이 낮을 수 있다.

## 자원 한도

- CPU 비율은 논리 코어 수에 대한 Worker 수와 작업/휴식 비율이다. GPU를 사용할 수 없다고 CPU 한도를 높이지 않는다.
- GPU 비율은 구간 처리·읽기 후 쉬는 시간을 정한다. 100%는 앱에서 추가 휴식을 넣지 않는 설정이다. GPU를 강제로 100% 점유시키는 설정이 아니다.
- RAM 비율은 입력·출력·업로드·CPU Worker 입력 복사·GPU 버퍼와 여유 공간을 포함한 앱 버퍼 예산이다. 브라우저가 알려주는 메모리 용량은 근사치이며 알 수 없으면 512 MiB를 기준으로 삼는다. 앱 예산은 최대 512 MiB로 제한한다.
- CPU/GPU 0%는 해당 연산 경로를 끈다. 둘 다 0%이거나 RAM 예산이 부족하면 참여할 수 없다.
- 한도 변경은 즉시 작업을 중단하고 동의를 철회한다. 새 한도는 다시 참여해야 적용한다. 같은 PC의 여러 탭은 각 탭의 사용량이 합산된다.

## MVP 제한

| 항목 | 제한 |
| --- | --- |
| 업로드 | 파일당 64 MiB, MP4·MOV·WebM |
| 길이 | 최대 30초, 초과 입력은 거절 |
| 입력 크기 | 각 변 최대 4096픽셀 |
| 처리 크기 | 최대 1280×720, 원본 비율 유지, 짝수 크기 |
| 출력 | 24fps, 최대 720프레임, H.264/AAC MP4 |
| 오디오 | 원본의 첫 오디오 트랙 유지, AAC로 정규화 |
| 동시 작업 | 준비 1개, 분산 처리 최대 2개 |
| 저장 예산 | 서버 전체 원본·중간 결과 예약 합계 4.5 GiB |
| 기기별 작업 | 활성 프레임 1개, 한정된 CPU Workers·GPU 구간 |

원본 프레임을 RGBA로 전송하므로 720p 한 프레임은 약 3.52 MiB다. 30초 영상은 원본 전송과 처리 결과 회신 각각 약 2.47 GiB가 될 수 있다. 작은 영상이나 느린 인터넷에서는 단일 PC보다 느릴 수 있다. 실사용 규모 확장은 압축 프레임/청크 전달, WebCodecs, 영속 저장소, 더 큰 서버와 스케줄러가 필요하다. MVP는 큰 영상을 조용히 자르거나 GPU 가속 인코딩까지 제공한다고 주장하지 않는다.

업로드 원본·프레임·결과는 임시 저장소에 둔다. 방 만료·정리·정상 서버 종료 시 삭제되며 서버 재시작 후 복구하지 않는다. 로컬 프로세스의 강제 종료나 시스템 충돌 뒤에는 OS 임시 폴더에 잔여 파일이 남을 수 있으므로 운영 시 임시 저장소의 수명도 관리한다. 초대된 참여자는 맡은 원본 프레임을 볼 수 있고 초대 링크로 결과를 볼 수 있다. 공유할 수 있는 영상으로 시연한다.

## 검증

`pnpm test`는 필터의 의미·경계·정수 계산, 파일 검사·동의·lease·재배정·취소와 실제 FFmpeg 오디오/영상 조립을 확인한다. `pnpm test:e2e`는 업로드 파일을 세 브라우저가 실제 Worker로 처리하고 모든 제출 RGBA를 CPU 기준 결과와 비교한다. 다운로드한 MP4에서 오디오를 디코딩해 소리가 유지되는지도 확인한다.

하드웨어 GPU 검증:

```powershell
$env:REQUIRE_WEBGPU = '1'
pnpm exec playwright test tests/e2e/video-gpu.spec.ts tests/e2e/video.spec.ts
Remove-Item Env:REQUIRE_WEBGPU
```

GPU가 없는 CI에서는 GPU 전용 사례만 건너뛴다. 위 환경변수를 설정한 검증에서는 실제 하드웨어 어댑터가 없으면 실패한다. 레거시 레이트레이서의 오차 허용 테스트와 달리 업로드 필터 테스트는 CPU와 GPU의 바이트가 정확히 같아야 통과한다.
