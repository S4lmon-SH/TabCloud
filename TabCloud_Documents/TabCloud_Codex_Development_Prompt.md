## 0. 역할과 작업 원칙

당신은 숙련된 풀스택·분산 시스템 엔지니어이자 오픈소스 유지관리자다. 현재 저장소에 **TabCloud Render의 실행 가능한 MVP**를 직접 구현하라.

먼저 저장소 파일과 기존 변경사항을 살펴보고 `TabCloud_Project_Overview.md`를 읽어라. 개요서를 제품 요구사항의 근거로 삼되, 아래 구체적인 MVP 범위·안전 제약·완료 기준을 우선 적용하라. 기존 코드가 있다면 가능한 한 재사용하고, 사용자의 미완료 변경을 임의로 덮어쓰거나 삭제하지 마라.

**반드시 실제 코드를 작성하고 실행 가능한 결과물을 만들어라.** 계획이나 README만 만들고 끝내지 마라. 프런트엔드의 계산 결과·진행률·참여자 수를 가짜 타이머나 하드코딩된 데이터로 꾸미지 마라. 기능이 동작하지 않으면 동작하지 않는다고 명확히 표시하라.

질문이 없으면 스스로 합리적인 기술 결정을 내려 계속 진행하라. 다만 기존 저장소와 충돌하는 심각한 변경, 인증 정보 필요, 외부 유료 리소스 사용처럼 사용자의 판단이 필요한 일은 무단으로 진행하지 마라.

## 1. 구현할 제품

**TabCloud:** 누구나 웹페이지에서 임시 연산방을 만들고 초대 링크로 참여자를 모아, 참여자가 동의한 브라우저 CPU에서 **Mandelbrot 프랙털 이미지의 타일을 실제로 병렬 계산**하는 분산 렌더링 도구.

최초 사용 흐름:

1. 방장이 웹사이트에서 방을 생성한다.
2. 해상도, 반복 횟수, 프랙털 범위 등 지원 설정을 선택한다.
3. 초대 링크를 복사하여 다른 사람에게 공유한다.
4. 참여자는 작업 설명을 읽고 **명시적으로** 연산 참여를 누른다.
5. 서버가 독립적인 타일 작업을 분배한다.
6. 참여 브라우저는 Web Worker에서 픽셀 계산을 수행한다.
7. 방장 화면은 완료된 타일을 캔버스에 실시간으로 합성한다.
8. 기기 이탈·타임아웃 때 미완료 작업을 재배정한다.
9. 모든 타일이 완성되면 PNG를 다운로드한다.
10. 동일 설정의 단독 실행 기준과 분산 실행 시간을 비교한다.

서버는 **작업 조율자**여야 하며 모든 픽셀을 대신 계산하는 중앙 렌더 서버가 되어서는 안 된다. 실제 픽셀 계산의 주 실행 위치는 참여 브라우저다.

## 2. MVP 범위와 제외 항목

### 반드시 구현

- 방 생성·초대 링크·방장 관리 권한 분리·방 만료
- 참여자 연결/해제 상태, 명시적 참여/중단, 기여 작업 수
- Mandelbrot 프랙털 렌더링, 타일 분할, 진행률, 완성된 타일의 점진적 표시
- Web Workers에서 계산하고 WebSocket으로 결과 전송
- 동적 pull 기반 스케줄링(처리가 끝난 참여자가 다음 작업을 요청)
- timeout/lease/heartbeat에 따른 작업 재할당
- 중복·지연 결과의 idempotent 처리, 결과 정확성 검사
- 분산 실행 완료, 취소, 작업 실패 상태
- 완료된 캔버스의 PNG 내보내기
- 단일 기기 기준과 다중 기기 작업의 실제 wall-clock 시간 측정·표시
- 웹 UI, 테스트, Docker, 사용 문서, GitHub CI

### 만들지 말 것

- 사용자가 업로드한 임의 JavaScript/Python/WASM 코드의 실행
- 브라우저 밖 시스템 접근, 파일 탐색, 암호화폐 채굴, 백그라운드 무단 연산
- 사용자의 실데이터 업로드를 전제로 하는 작업
- 범용 AI 학습, Blender 렌더팜, WebRTC P2P, 회원·결제 서비스
- 프로덕션급 다중 서버/Redis 기반 클러스터링(향후 확장점만 설계)

## 3. 권장 기술 스택과 프로젝트 구조

가능하면 아래를 사용하되, 의존성 간 충돌이 있으면 **현재 안정적으로 설치·빌드·테스트되는 호환 버전**을 선택하고 이유를 기록하라.

- **Monorepo:** pnpm workspaces + TypeScript
- **Web:** React + Vite + TypeScript, Canvas API, Web Worker
- **API/Coordinator:** Node.js + Fastify + WebSocket(`ws` 또는 안정적인 Fastify 연동)
- **Shared:** 프로토콜 타입 및 Zod 런타임 검증 스키마
- **Tests:** Vitest(단위/통합), Playwright(브라우저 E2E)
- **Deploy:** Dockerfile + compose.yaml, 하나의 도메인에서 HTTP와 WebSocket 제공

권장 파일 구조(기존 저장소가 있다면 조정 가능):

```text
tabcloud/
  apps/
    web/                 # 방 생성/참여/시각화 UI
    server/              # API, WebSocket, room/task coordinator
  packages/
    shared/              # 메시지 타입·입력 스키마·상수
    compute/             # Mandelbrot 계산/타일 규약, worker 재사용 가능 순수 함수
  tests/                 # 통합/E2E
  docs/                  # 아키텍처, 개발·시연·배포 설명
  Dockerfile
  compose.yaml
  .env.example
  .github/workflows/ci.yml
  README.md
```

개발용 `pnpm dev`, `pnpm test`, `pnpm build`, `pnpm lint` 같은 실행 명령을 루트에 제공하고, 각 명령이 실제로 동작하는지 확인하라. 설치 프로그램이 없는 환경이라면 실행하지 못한 명령과 이유를 결과에 남겨라.

## 4. 연산의 정밀한 정의

처음 지원할 작업 종류는 **Mandelbrot 프랙털 렌더링 하나**다. 이미지 크기, `maxIterations`, viewport(중심/확대 정도), 타일 크기를 입력받는다. 서버는 값을 검사하고 허용 범위를 제한한다.

권장 기본값(조정 가능):

- 이미지: 1024×1024
- 타일: 128×128, 총 64개
- 반복 횟수: 500
- 프랙털 좌표: 널리 쓰이는 기본 Mandelbrot viewport

한 타일에는 `jobId`, `taskId`, 타일 위치 `(x, y)`, 너비·높이, 원본 이미지 크기, 좌표 범위, 반복 횟수, 알고리즘 버전 등을 포함한다. 같은 입력이면 어느 기기에서 계산해도 결정적인 동일 결과가 나와야 한다. 색상 팔레트와 픽셀 좌표 매핑을 고정하고 공유 순수 함수에서 테스트하라.

계산은 UI 메인 스레드가 아니라 **Web Worker**에서 수행하라. `ImageData`/바이너리 배열 혹은 제한된 크기의 안전한 인코딩으로 결과를 전송하라. 가능하다면 ArrayBuffer transferable을 사용하되 서버 전송 형식과의 호환성을 검증하라. 각 타일 데이터 크기 및 전체 작업 메모리 사용량에 상한을 둬라.

방장은 같은 기기에서 연산 참여 여부를 선택할 수 있어야 한다. 참여하지 않더라도 화면에서 결과를 볼 수 있어야 한다.

## 5. Coordinator·작업 상태 머신

각 작업의 상태를 명확하게 정의하라.

`pending → leased → completed`를 기본으로 하고, 만료·연결 종료 시 `leased → pending`으로 되돌린다. 방의 전체 작업은 `created / running / completed / cancelled / failed`로 관리한다.

필수 동작:

1. 참가자가 동의를 누르고 `ready/request-task`를 보낸 경우에만 작업을 할당한다.
2. 작업은 한 번에 허용된 수만 할당하며, 과부하가 되지 않도록 한다.
3. 작업 배정 시 고유 `attemptId`와 기한(`leaseUntil`)을 부여한다.
4. Worker 종료·WebSocket 이탈·lease 만료 때 미완료 작업을 다시 큐에 넣는다.
5. 오래된 attempt에서 도착한 결과는 무시하고, 동일 `taskId`를 중복 반영하지 않는다.
6. 완료 작업 수는 **유효하게 승인된 고유 taskId**를 기준으로 집계한다.
7. 완료 시 모든 타일이 있는지 검사한 뒤 최종 상태를 `completed`로 바꾼다.
8. 방장이 취소하면 추가 배정을 멈추고 Worker에 중단 메시지를 보낸다.
9. 방 또는 참여자가 비정상 동작해도 서버 프로세스가 죽지 않도록 입력을 검증하고 예외를 처리한다.
10. 방이 끝나거나 만료되면 WebSocket·작업 메모리·결과 버퍼를 정리한다.

**Heartbeat와 타임아웃:** 연결이 살아 있다는 신호와 개별 작업의 완료 신호는 구분하라. 느리지만 정상적인 계산이 무조건 반복 재할당되지 않도록 lease 정책을 문서화하고, 작업 진행 알림 또는 적절한 상한 시간/연장 전략을 적용하라.

### 권장 이벤트 규약(변경 가능)

- 클라이언트 → 서버: `join-room`, `consent-compute`, `request-task`, `task-result`, `task-error`, `heartbeat`, `leave-room`, `start-job`, `cancel-job`
- 서버 → 클라이언트: `room-snapshot`, `participant-update`, `task-assigned`, `task-accepted`, `task-rejected`, `tile-completed`, `job-progress`, `job-completed`, `job-cancelled`, `error`

모든 메시지는 명시적인 `type`, 프로토콜 버전, 필요 시 room/job/task/attempt ID를 포함하라. 연결별 역할과 방장 전용 권한을 서버에서 검증하라. 어떤 클라이언트 메시지도 타입·크기 검증 없이 신뢰하지 마라.

## 6. 정확성·신뢰 경계

브라우저는 신뢰할 수 없는 계산 노드다. 임의의 결과를 올리는 참여자가 있을 수 있으므로 다음을 구현하라.

- 최소한 타일 범위, 픽셀 버퍼 크기, `jobId/taskId/attemptId`, 중복 여부를 엄격하게 검증
- 가능한 범위에서 결과의 표본 픽셀을 서버에서 재계산하거나 신뢰 가능한 기준 계산과 비교(검증에 든 비용은 별도 측정)
- 오류가 의심되면 해당 작업을 재배정하거나 실패로 표시
- 결과 정확성 테스트: 단독 실행 기준 이미지와 분산 결과의 전체 픽셀 또는 해시 비교

**주의:** 표본 검증은 악의적 참여자에 대한 완전한 무결성을 증명하지 않는다. MVP의 위협 모델과 한계를 README에 명시하라.

## 7. 웹 UI와 사용자 경험

디자인은 과도한 애니메이션보다 이해하기 쉬운 정보 구조가 우선이다. 반응형·접근성 고려, 한국어 UI를 기본으로 하라. 다음 화면을 제공하라.

1. **홈:** 짧은 제품 설명, `방 만들기`, `초대 링크로 참여`.
2. **방장 화면:** 방 코드/초대 링크 복사, 렌더 설정, 참가자 목록, 시작/취소, 진행 상황, 결과 이미지.
3. **참가자 화면:** 참여할 계산의 종류, CPU 사용 안내, `연산 참여` / `중단`, 현재 담당 작업 수.
4. **진행 상황:** 타일이 채워지는 캔버스, 전체 진행률, 참여자별 완료 수, 연결 상태, 재할당 메시지.
5. **완료 화면:** 최종 이미지 PNG 다운로드, 전체 처리 시간, 오류/재시도 요약, 단독 실행 결과와 비교.
6. **오류/엣지 케이스:** 유효하지 않거나 만료된 방, 방장 이탈, 네트워크 재연결, 브라우저 Worker 미지원, 서버 재시작.

**중요:** 진행률과 장치 참여 수는 WebSocket으로 받은 실제 서버 상태에서 계산하라. 대시보드 목업용 샘플 수치를 실제 측정값인 것처럼 표시하지 마라. 불완전한 기능은 숨기거나 `개발 예정`이라고 표시하라.

## 8. 단독 실행 비교와 벤치마크

성능을 오해 없이 보여줘야 한다. **한 컴퓨터의 단독 실행**과 **실제 여러 컴퓨터의 분산 실행**을 동일한 이미지 크기·좌표·반복 횟수·색상 규약으로 측정하라.

- 측정 값: 작업 시작에서 최종 이미지 완성까지 wall-clock 시간, 작업 처리 시간, 결과 전송/조율 오버헤드(관찰 가능한 범위), 완료 타일 수, 재시도 횟수.
- 단독 실행 기준: 동일 브라우저 계산 엔진을 로컬에서 실행하되 worker 수·기기 조건을 명확히 표기.
- 분산 실행 기준: 각 참여자에 실제 배정된 타일 수와 총 소요 시간 표시.
- 속도 향상은 `단독 실행 시간 / 분산 실행 시간`으로 계산하고, 검증되지 않은 수치를 하드코딩하지 마라.
- 한 컴퓨터에서 브라우저 탭 3개를 띄운 기능 테스트를 물리적 컴퓨터 3대의 성능 측정으로 주장하지 마라.
- 예측된 절감 시간과 실측 값은 명확히 분리하라.

자동화 테스트에서는 실제 세 기기 사용을 전제로 하지 말고 다중 브라우저 컨텍스트를 통해 기능을 검증한다. 실제 성능 시연 방법은 `docs/DEMO.md`에 별도 문서화하라.

- 참여하기 전 작업 설명과 자원 사용 안내를 보여주고 사용자의 **명시적 클릭 후에만** 계산 시작.
- 언제든 중단 가능. 탭이 숨겨지거나 브라우저 환경이 제한될 수 있음을 표시.
- CPU 사용률을 정밀하게 제어할 수 있다고 거짓 주장하지 마라. 초기에는 동시 Worker 수(예: 1~2)와 작업 크기, 사용자 중단으로 제어.
- 방 ID와 초대 토큰은 추측하기 어렵게 생성하고, 방장 관리 권한은 참여 링크와 분리.
- 서버에서 메시지 크기, 해상도·반복 횟수, 참여자 수, 방 생성 수, 결과 페이로드 크기, 요청 빈도, 작업 실행 시간, 방 수명을 제한.
- 웹·API와 WebSocket은 실배포에서 HTTPS/WSS를 사용하고, 적절한 origin 검사와 기본 보안 헤더를 설정.
- 민감 파일, 카메라, 마이크, 로컬 시스템 권한 요청을 하지 마라.
- 사용자가 제공한 임의 코드를 다른 사용자의 브라우저에서 실행하지 마라.
- 참여자·방장은 가능하면 가명 또는 랜덤 표시명으로 표시하고 개인 식별 정보 수집을 최소화.
- MVP 인메모리 방 상태는 서버 재시작 시 유실된다는 점을 문서에 명시.
- 실제 브라우저 CPU 참여를 숨기거나 사용자를 속이는 기능은 만들지 마라.

## 10. 반드시 테스트할 시나리오

단위/통합/E2E 테스트를 작성하고 가능하면 실제로 실행하라.

1. 동일한 렌더 설정에서 타일 분할이 전체 픽셀을 누락·중복 없이 덮는지.
2. Mandelbrot 계산이 결정적으로 동일한 결과를 내는지.
3. 1개 참여자와 3개 참여자(브라우저 컨텍스트)에서 최종 이미지가 동일한지.
4. 작업 중 참여자가 연결을 끊으면 lease 만료 또는 disconnect 처리 후 작업이 재배정되는지.
5. 늦게 들어온 예전 `attemptId`와 중복 결과가 완료 수·이미지에 중복 반영되지 않는지.
6. 방장만 작업 시작/취소가 가능한지.
7. 연산 참여 동의 이전에 브라우저가 계산을 시작하지 않는지.
8. 참여 중단 시 새로운 작업을 요청하지 않고 활성 Worker를 종료하는지.
9. 잘못된 스키마·초과 페이로드·불법 설정에 서버가 안전하게 오류를 반환하는지.
10. 작업 완료 시 PNG 다운로드가 가능한지.
11. 방 만료·서버 재시작 등 제한 상황에서 사용자에게 적절한 안내가 표시되는지.
12. `pnpm build`와 Docker 빌드가 성공하는지.

가능하면 Playwright로 **방장 1개 + 참여자 2개 컨텍스트**를 실행하는 E2E 스크립트를 만들라. 이는 다중 물리적 컴퓨터 테스트의 대체물이 아니라 기능 테스트다.

## 11. 로컬 실행·공개 배포

제공해야 할 산출물:

- 실행 가능한 전체 소스코드와 명확한 디렉터리 구조
- `README.md`에 프로젝트 소개, 요구 사항, 설치, 환경변수, 실행 명령, 보안 주의사항
- `.env.example`: 서버 포트, 방·연산 제한, 공용 URL 등 비밀이 아닌 기본 환경변수 예시
- `Dockerfile`, `compose.yaml`: 단일 소형 서버에서 구동 가능
- HTTP 정적 웹 UI와 WebSocket의 **동일 출처 연결** 또는 명확한 프록시 설정
- `/healthz` 같은 헬스체크 API
- `docs/ARCHITECTURE.md`: 상태 머신, 메시지 규약, 데이터 흐름
- `docs/DEMO.md`: 기기 3대 시연, 이탈 실험, 단독/분산 성능 비교 방법
- `docs/DEPLOYMENT.md`: Docker 배포 및 HTTPS/WSS 리버스 프록시 예시, 비용이 발생할 수 있다는 주의사항
- `LICENSE`(MIT), `.gitignore`, 최소 GitHub Actions CI

실제 퍼블릭 클라우드 계정, 도메인, 유료 서비스나 API 비밀키가 없다면 **임의로 발급·구매·배포하지 말고**, 로컬 실행 가능한 Docker 배포 결과와 실제 서버에 배포하는 명령을 제공하라. 필요한 외부 리소스는 최종 결과에 명시하라.

## 12. 단계별 개발 순서

아래 순서대로 하나씩 동작하는 상태를 만들면서 개발하라.

**Phase 1 — 부팅 가능한 뼈대**

- 워크스페이스, React 웹, Fastify 서버, 공용 타입, WebSocket 연결.
- 브라우저에서 방 생성/참여가 실제로 동작하는 상태.

**Phase 2 — 단일 연산 완주**

- Mandelbrot 순수 계산 함수, 타일 분할, Worker, 하나의 작업 완주, 캔버스 합성.
- 브라우저 단독 계산 기준 이미지와 일치 테스트.

**Phase 3 — 실시간 분산 실행**

- 작업 큐, 다중 참여자, pull 기반 동적 할당, 타일 실시간 합성.

**Phase 4 — 이탈 복구와 정확성**

- heartbeat/lease/attempt, 재할당, 오래된 결과 무시, 최소 결과 검증.

**Phase 5 — 사용자 제품화**

- 동의/중단, 반응형 UI, PNG 다운로드, 통계/비교, 방 만료 및 예외 상태.

**Phase 6 — 품질/배포**

- 단위·통합·E2E 테스트, 보안 한계 점검, Docker, CI, README 및 시연 가이드.

각 Phase에서 가능한 범위의 테스트를 실행하여 회귀를 줄여라. 범위를 키우느라 핵심 기능 완성을 희생하지 마라.

## 13. 완료 판정(Definition of Done)

아래 항목이 모두 만족되어야 'MVP 완료'로 보고한다.

- [ ] `pnpm install`, `pnpm dev`로 서버와 프런트엔드 실행 가능
- [ ] 웹에서 방 생성 후 다른 브라우저가 초대 링크로 접속 가능
- [ ] 2개 이상의 별도 브라우저 컨텍스트에서 **실제 Web Worker**가 계산 수행
- [ ] 프랙털 타일이 진행률에 따라 실시간 캔버스에 채워짐
- [ ] 한 참여자 연결 종료 후 미완료 작업이 다른 참여자에게 재할당됨
- [ ] 중복·오래된 결과가 진행률 또는 이미지에 두 번 반영되지 않음
- [ ] 기준 단독 실행 결과와 최종 이미지가 일치함
- [ ] 명시적인 연산 참여 동의와 중단 기능 동작
- [ ] 작업 완료 후 PNG 다운로드 가능
- [ ] 실측한 단독/분산 처리 시간이 구분되어 표시됨
- [ ] 최소 핵심 테스트 통과, 빌드 성공, Docker 빌드 확인
- [ ] README/아키텍처/시연/배포 설명서 및 오픈소스 라이선스 포함

**합격 기준에는 무조건적인 속도 향상을 넣지 마라.** 성능 향상은 측정 결과로 판단한다.

## 14. 결과 보고 방식

작업을 마친 뒤 다음 순서로 한국어로 보고하라.

1. **실제로 구현한 기능**과 주요 폴더·파일 설명.
2. **로컬 실행 명령**, **Docker 실행 명령**, 브라우저에서 테스트하는 단계.
3. 실행한 **테스트·빌드 명령과 성공/실패 결과**. 실제 실행하지 않은 테스트를 성공했다고 쓰지 마라.
4. 방장 1명과 참여자 2명이 등장하는 **실제 시연 절차**.
5. 완료 기준별 충족 여부, **미구현 항목과 알려진 버그**.
6. 보안·성능·브라우저 호환성의 남은 제한.
7. 필요 시 다음 단계에서 구현할 수 있는 SDK·템플릿·WASM 확장 제안.

최종 산출물은 **코드가 실행되고, 브라우저에서 실제로 분산 계산되고, 기기 이탈 후에도 작업이 완수되는 상태**여야 한다. 단순한 목업, 가짜 진행률, 하드코딩된 그래프, 설계 문서만으로 완료 처리하지 마라.
