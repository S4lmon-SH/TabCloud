# TabCloud 실제 시연과 측정

기본 홈페이지의 **3D 영상 렌더팜** 시연은 [영상 시연 가이드](ANIMATION.md)를 사용한다. 아래 내용은 `/fractal`에서 시작하는 기존 프랙털 모드의 검증 절차다.

이 문서는 실행 절차와 관찰 기준을 제공한다. 아래 절차를 작성했다는 사실만으로 물리적 기기 3대의 시연이나 성능 측정을 완료했다고 주장하지 않는다. 자동화 검증 결과는 실제 실행 기록과 함께 별도로 보고한다.

## 1. 준비

서버를 실행할 컴퓨터 1대와 현재 버전의 Web Worker 지원 브라우저가 있는 물리적 기기 3대를 준비한다. 서버 컴퓨터가 방장 브라우저를 함께 실행해도 된다. 같은 신뢰할 수 있는 LAN을 사용하고, 노트북·모바일의 발열·배터리·절전 상태를 확인한다. 외부에 공개할 때는 [배포 안내](DEPLOYMENT.md)의 HTTPS/WSS 구성을 따른다.

프로젝트 루트에서 다음을 실행한다.

```sh
pnpm install
pnpm dev
```

개발 웹 주소는 `http://localhost:5173`, 내부 Coordinator는 기본 `3001` 포트다. 다른 물리적 기기에서는 `localhost`가 각자의 기기를 가리키므로, 서버 컴퓨터의 실제 LAN IPv4 주소로 바꿔 접속한다. 예를 들어 서버 주소가 `192.168.0.20`이면 3대 모두 `http://192.168.0.20:5173`을 연다. 예시 IP는 자신의 환경 값으로 바꾼다. Windows에서는 `ipconfig`로 현재 연결의 IPv4를 확인할 수 있다. 신뢰하는 네트워크에서 해당 웹 포트로 들어오는 연결이 방화벽에 허용되어야 한다.

초대 링크와 방장 자격이 같은 출처에 유지되도록 방장은 **처음부터 LAN 주소로 접속하여 방을 만든다.** `localhost`에서 만든 방을 뒤늦게 LAN 주소로 바꾸면 브라우저 저장소의 출처가 바뀌어 방장 토큰을 사용할 수 없다. 그 경우 LAN 주소에서 새 방을 만든다. 개발 모드는 Vite가 API와 WebSocket을 프록시하므로 다른 기기가 Coordinator 포트로 직접 접속할 필요가 없다.

빌드 결과로 시연할 경우에는 다음을 사용하고 3대 모두 `http://서버-LAN-IP:3001`을 연다.

```sh
pnpm build
pnpm start
```

`PUBLIC_ORIGIN`을 지정한 배포 환경이라면 실제로 접속하는 origin과 일치시킨다. LAN의 평문 HTTP에서 브라우저가 클립보드 API를 막으면 초대 링크 입력란을 선택하여 직접 복사한다.

## 2. 방장 1명과 참여자 2명의 기본 시연

1. 기기 A를 방장으로 정하고 `방 만들기`를 누른다. `방장` 배지와 서버 연결 상태를 확인한다.
2. 방장의 `초대 링크 복사`로 전체 링크를 전달한다. 기기 B와 C는 링크를 직접 열거나 홈의 `초대 링크로 참여`에 붙여 넣는다. 링크의 `#invite=...` 부분을 생략하지 않는다.
3. 3개 화면의 연결 목록에 같은 참가자들이 보이는지 확인한다. 참가 직후 각 브라우저는 `지금은 구경 중`이어야 한다. 연결되어 있다는 이유만으로 Worker가 연산하지 않는다.
4. 방장에서 기본 선택된 **시연용**을 확인한다. 너비·높이 `2048`, 반복 `8000`, 타일 `128`이며 중심 `(-0.5,0)`, 가로 범위 `3.5`를 사용한다. 예상 타일은 256개다. 빠른 점검만 필요하면 **가볍게**(`1024² / 500회`, 64타일)를 선택한다. 숫자·좌표는 **직접 설정**에서 변경할 수 있다.
5. 각 사용자가 CPU 사용·발열·배터리 안내를 읽고 직접 `연산 참여`를 누른다. 3대 모두 연산하는 시연에서는 A도 참여한다. 방장 A가 관찰만 하고 B·C만 연산하는 변형도 가능하며, 이 경우 실제 연산 기기는 2대라고 기록한다.
6. 준비된 뒤 A가 `렌더 시작`을 누른다. 완료된 타일이 캔버스에 점진적으로 표시되고, 실제 완료 수·각 기여자의 타일 수가 증가하는지 확인한다. 기기 속도에 따라 기여 타일 수가 같을 필요는 없다.
7. `렌더 완료`, 전체 타일 완료 및 수신을 확인한다. **측정 정보**를 펼쳐 A·B·C의 `이미지 체크섬`이 같은지 기록한다. 각 브라우저의 `PNG 다운로드`로 이미지를 저장한다.
8. 화면의 연산 기록, 참가자별 완료 수, 설정, 서버·화면 완성 시간을 남긴다. 실제 서로 다른 타일을 처리한 기여자가 2명 이상인지 확인한다. 작은 작업이 너무 빨리 끝나 한 기기만 처리했다면 다음 작업에서 아래의 큰 설정을 사용한다.

상대적으로 긴 시연이 필요하면 **최대 부하**(`2048² / 20,000회`)를 선택한다. CPU 사용이 늘어나므로 모든 참여자에게 알리고 선택한다. 범위 상한은 각 변 2048, 반복 20,000, 타일 32/64/128, 전체 4096타일이다. 허용 범위 내에서도 느린 기기에서는 attempt 120초·전체 작업 10분 제한에 걸릴 수 있다. 성공 여부를 꾸미기 위해 타임아웃을 숨기지 않는다. 프리셋 변경만으로 연산이 시작되지 않으며 모든 모드의 동시 Worker는 1개다.

## 3. 중단·연결 이탈·복구 시연

### 사용자의 즉시 중단

1. A와 B·C를 참여시킨 뒤 충분히 큰 작업을 시작한다.
2. B가 `계산 중이에요`일 때 `연산 중단`을 누른다.
3. B는 관찰 모드로 돌아가고 새로운 작업을 가져가지 않아야 한다. 진행 중 Worker는 종료된다. 방 자체에는 남아 결과를 볼 수 있다.
4. B의 미완료 타일은 회수되어 남은 동의한 기기에 다시 배정된다. A·C의 작업이 진행되고 최종 완료에 도달하는지 확인한다.

### 탭 종료 또는 네트워크 단절

1. 새 작업에서 B가 실제로 타일을 계산 중임을 확인하고 탭을 닫는다. 이미 타일을 완료한 뒤 종료하면 재시도가 생기지 않을 수 있으므로 활성 작업 상태를 먼저 확인한다.
2. A의 연결 목록에서 B가 연결 종료로 표시되고 재할당·재시도 기록이 생기는지 확인한다. 정상 소켓 종료는 바로 처리되지만 갑작스러운 네트워크 단절은 heartbeat timeout 기본 20초와 검사 주기만큼 걸릴 수 있다. 타일 lease는 기본 15초이고 정상적인 진행 알림으로 연장된다.
3. A·C가 나머지 타일을 끝내는지 확인한다. 완료 수는 전체 타일 수를 초과하지 않아야 하며 완성 이미지가 단독 기준과 일치해야 한다.
4. B가 같은 링크로 다시 접속하면 완료된 타일을 재수신한다. 자동으로 연산을 재개하지 않아야 한다. 사용자가 다시 `연산 참여`를 눌러야 다음 작업을 받는다.

클라이언트를 모두 중단하면 처리할 기기가 없으므로 실행 중인 작업은 기다리다가 전체 시간 제한으로 실패할 수 있다. 복구 실험에서는 적어도 한 브라우저의 동의를 유지한다. 단순 탭 종료는 disconnect 회수를 보여주는 절차이며, 오래된 attempt·중복 결과·lease 만료 같은 경쟁 조건은 통합 테스트가 별도로 확인한다.

### 방장의 취소와 관찰 모드

방장 A가 `작업 취소`를 누르면 추가 배정이 중지되고 모든 브라우저의 해당 작업 Worker가 정지해야 한다. 부분 이미지는 완성본 PNG로 제공하지 않는다. 새 작업을 시작하면 이전 Canvas가 초기화된다. 참여자에게는 작업 시작·취소 관리 권한이 없다.

방장 A의 탭을 닫아도 이미 시작된 작업은 남은 참여자로 계속 진행할 수 있다. 방장 자격이 남은 동일한 탭·출처로 돌아오기 전에는 새 작업을 관리할 수 없다. 원래 방장 탭을 완전히 닫아 sessionStorage가 사라진 경우 링크만으로 방장 권한이 복구되지 않는다. 권한 이전 기능은 제공하지 않는다.

## 4. 단독·분산 측정

1. 측정할 기기 A와 네트워크를 정하고 설정을 고정한다. 분산 측정 전에 참여할 기기들의 동의를 완료한다. 렌더를 먼저 시작한 뒤 사람을 기다린 시간도 wall-clock에 포함된다.
2. A에서 새 분산 작업을 시작하고 완료를 기다린다. A의 `분산 실행 · 화면 완성`은 시작 메시지 전송부터 모든 타일 합성 후 다음 animation frame까지의 실측 시간이다. 서버 작업 시작→최종 승인 시간은 별도로 제공한다.
3. 같은 A에서 `단독 실행 측정`을 직접 누른다. 이 동작은 동일 설정을 Worker **1개**로 계산하며 CPU를 사용한다. Worker 생성, 타일 계산, Canvas 합성, 체크섬 시간이 단독 wall-clock에 포함된다. `연산 중단`으로 취소할 수 있다.
4. `단독 결과 일치`가 표시되는지 먼저 확인한 뒤 시간을 비교한다. 비율은 `단독 wall-clock / 분산 화면 완성 wall-clock`이다. 1보다 작으면 해당 조건에서 분산 실행이 더 느린 것이다.
5. 워밍업 여부를 기록하고 가능한 한 같은 조건으로 최소 3회 반복한다. 중앙값과 각 원시 측정값을 함께 남긴다. 작업마다 설정·기여자·연결 이탈·재시도·백그라운드 작업 상태가 달랐다면 같은 조건으로 묶지 않는다.

시작한 방장 브라우저가 재연결되거나 다른 브라우저가 뒤늦게 들어온 경우, 최초 로컬 시작 시각을 재구성하지 않는다. 해당 화면의 end-to-end 시간과 속도 비율은 제공되지 않을 수 있다. 이때 새 작업을 시작해서 측정한다. 서버 `wallMs`를 대신 넣어 서로 다른 구간의 수치를 같은 측정값으로 표시하지 않는다.

기록 표는 실제 값으로 채운다.

| 실행 | 기기·브라우저 / 실제 연산 기기 수 | 설정 | 분산 화면 완성 ms | 서버 wall ms | 단독 ms | 단독÷분산 | 체크섬 일치 | 재시도 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 미측정 | 미측정 | — | — | — | — | — | — |
| 2 | 미측정 | 미측정 | — | — | — | — | — | — |
| 3 | 미측정 | 미측정 | — | — | — | — | — | — |

`승인된 연산 시간 합계`는 각 클라이언트가 보고한 시간의 합이므로 병렬 wall-clock과 다르다. Worker가 청크 사이에 양보한 시간도 포함한다. `할당→결과 수신 시간 합계`도 기기별 구간이 겹치며 순수 네트워크 오버헤드가 아니다. RGBA 바이트 수는 base64·JSON·방송·재시도 전송량을 포함한 실제 네트워크 트래픽이 아니다. 성능 향상이나 1.5배 이상의 결과를 보장하지 않는다.

## 5. 만료와 서버 재시작 확인

- 기본 방 수명은 1시간, 모든 연결이 사라진 후 유휴 정리는 10분이다. 시연용 별도 서버에서 `ROOM_TTL_MS`나 `IDLE_ROOM_TTL_MS`를 짧게 설정하면 만료 동작을 빨리 확인할 수 있다. 실제 공동 작업 도중 운영 서버 설정을 바꾸지 않는다.
- 방을 연 상태에서 서버를 종료하면 브라우저는 연결 상실을 알리고 연산을 멈춘다. 서버를 다시 켜도 이전 인메모리 방은 복구되지 않는다. 기존 링크에서 안내를 확인하고 홈에서 새 방을 만든다.
- 초대 URL에서 fragment를 지우거나 존재하지 않는 방 링크로 접속하여 안내를 확인한다. 잘못된 링크가 연결된 방이나 실행 중인 다른 작업을 손상시키지 않아야 한다.

## 6. 자동화 테스트와 실제 기기 실험의 구분

```sh
pnpm test
pnpm lint
pnpm build
pnpm exec playwright install chromium
pnpm test:e2e
```

자동화는 같은 머신에서 여러 브라우저 컨텍스트를 열어 방장과 참여자의 세션·권한·실제 Worker·통신·이미지 합성을 검증한다. 이는 3개의 물리적 기기에서 얻은 성능 결과가 아니다. 테스트 실행 여부·통과 수·실패 이유는 해당 실행 로그를 기준으로 보고한다. 단위 테스트의 전체 픽셀 비교, 통합 테스트의 재할당·중복 처리, 브라우저 테스트의 사용자 흐름은 서로 보완한다.

시연의 완료 조건은 기능과 측정을 분리하여 기록한다. 서로 다른 물리적 기기에서 실제 타일을 처리했는지, 한 기기 이탈 후 완주했는지, 단독 결과와 일치했는지, PNG를 받았는지부터 확인한다. 속도는 그 조건에서 관찰된 결과로 보고한다.
