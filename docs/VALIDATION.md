# MVP 구현 검증 기록

검증일: **2026-10-11 (Asia/Seoul)**. 기존 요구사항 문서 두 개를 보존하고 새 워크스페이스를 구현했다. 아래 결과는 실제로 실행한 로컬 명령과 브라우저 결과이며, 원격 CI나 물리적 기기 3대의 실험 결과를 대신하지 않는다.

## 실행 환경

- Windows / PowerShell, Node.js **24.14.1**, pnpm **9.15.9**
- Docker Desktop Linux Engine **28.5.1**, Compose **2.40.3**
- Playwright **1.64.0**, Chromium **156.0.8078.4**
- Docker runtime: `node:24-alpine`, 일반 `node` 사용자

아래 초기 MVP 기록은 당시 실행 결과다. UI 개편·고부하 프리셋 적용 후 추가 검증은 문서 마지막에 기록했다.

Docker 실행 검증에 사용한 명령:

```sh
docker run -d --name tabcloud-mvp-validation --init \
  -p 127.0.0.1:3003:3001 \
  -e PUBLIC_ORIGIN=http://127.0.0.1:3003 tabcloud:mvp
```

PowerShell의 컨테이너 E2E 명령:

```powershell
$env:E2E_BASE_URL='http://127.0.0.1:3003'
pnpm test:e2e
Remove-Item Env:E2E_BASE_URL
```

`docker compose up` 자체를 통한 운영 검증은 별도로 실행하지 않았다. Compose 구성 검사와 동일 Dockerfile 이미지의 실제 컨테이너 브라우저 검증을 수행했다. 공개 HTTPS 도메인과 GitHub 원격 CI 실행도 이번 로컬 검증 범위에 포함하지 않았다.

## 테스트 내용

- Shared **48개**: 유효한 프로토콜과 엄격한 런타임 스키마, 숫자/설정/페이로드 범위.
- Compute **11개**: 좌표·고정 팔레트·결정성, 경계 타일 전체 커버, 임의 순서 병합과 기준 이미지 전체 픽셀 일치, 비동기 연산 진행·취소, 버퍼·알고리즘 검사.
- Server API/config **20개**: 실제 로컬 WebSocket을 통한 권한·동의·배정·검증·중복·오래된 attempt·연결 종료·동의 철회·진행 lease·heartbeat·시간/재시도 제한·만료/메모리 정리·입력/연결 제한·결과 재전송·1/3노드 이미지 일치.
- Coordinator **1개**: 느린 수신자를 연결 해제할 때 중첩 snapshot 전송이 오래된 연결 상태를 다시 표시하지 않는 회귀 검사.

브라우저 E2E 세 시나리오:

1. **1개와 3개 독립 컨텍스트:** 작업 시작만으로 동의가 생기지 않는지 확인. 실제 Worker 생성과 모든 참여자의 승인 타일 기여를 관찰. 512×384/64px/400회 반복 48타일 결과를 단독 기준과 전체 RGBA 바이트 비교. 브라우저 단독 측정 체크섬 일치, 다운로드 PNG 디코딩 후 동일 픽셀 확인, 늦게 들어온 관찰자의 타일 재수신 확인.
2. **중단과 이탈:** 768×768/128px/2000회 반복 작업에서 참여 중단 후 Worker 종료·추가 작업 미요청 확인. 다시 참여한 브라우저 컨텍스트를 종료한 뒤 실제 재배정 attempt·재시도·연결 이탈 기록을 확인. 연산에 참여하지 않은 방장 화면에서도 남은 참여자의 완성 결과가 기준 전체 픽셀과 일치하는지 확인.
3. **취소와 없는 방:** 방장 취소 시 Worker 종료 및 PNG 비활성화, 존재하지 않는 방의 만료/재시작 안내 확인.

중단·종료 직전의 마지막 수신 frame은 브라우저 종료와 다음 배정의 경쟁 때문에 실제 최종 lease와 다를 수 있다. 따라서 이탈 검사는 전체 배정 기록의 새 attempt, 명시적 이탈 재배정 이벤트, 재시도 수, 최종 전체 픽셀을 함께 확인한다. 같은 타일이 여러 번 재시도될 수 있으며, 재시도 횟수와 서로 다른 재배정 타일 수를 동일하게 취급하지 않는다.

## 남은 제한

검증된 범위에서 재현 중인 핵심 기능 오류는 없다. 다음은 지원 범위와 운영상의 제한이다.

- 표본 검증은 악의적 노드의 전체 무결성 증명이 아니다. UI의 FNV 체크섬도 암호학적 인증 수단이 아니다.
- 저장소가 인메모리이므로 재시작 시 방·결과가 사라진다. 방장 탭의 세션 자격을 잃었을 때 복구·양도 기능은 없다.
- CPU 점유율 강제 제한 대신 Worker 1개·입력 한도·즉시 종료를 사용한다. 브라우저 백그라운드/절전 정책과 기기 성능은 통제하지 못한다.
- 자동 E2E는 Chromium만 실행했다. Safari/Firefox와 실제 다른 하드웨어는 추가 검증이 필요하다.
- 표시한 성능비는 각 실행의 관찰값이다. 물리적 3기기 가속이나 1.5배 향상을 주장하지 않는다.
- 보안 헤더·origin·quota 등은 기본 방어이며 프로덕션급 인증·DDoS 방어·다중 서버 영속 운영을 구현한 것은 아니다.
- 최대 입력 조합 중 2048²/32px 타일은 기본 작업 메모리 예산을 초과한다. 더 큰 타일을 사용하면 같은 해상도를 지원한다.
- WebRTC, WASM, SDK, 사용자 임의 코드, 회원·결제·장기 저장은 요구사항에 따라 제외했다.

구현 과정의 초기 타입·lockfile 불일치와 개발 프록시 Origin 오류, E2E의 재배정 개수 가정은 수정 후 재검증했다. 위 표는 수정 이후의 성공 결과를 기록한다.

## UI 개편·고부하 프리셋 추가 검증 (2026-10-11)

밝은 카드 UI와 접힌 상세 설정, 모바일 조작 순서를 적용했다. 새 방은 시연용 `2048×2048 / 8,000회 / 128px 타일`로 시작하며, 가볍게와 최대 부하(`20,000회`)를 선택할 수 있다. 실제 연산 엔진과 브라우저당 Worker 1개, 명시적 동의·중단 동작은 유지했다.

| 검증 | 결과 |
| --- | --- |
| `pnpm lint` | ESLint 및 전체 TypeScript 검사 성공 |
| `pnpm test` | **85개 통과 / 4개 파일** (shared 51, compute 13, server 20, coordinator 1) |
| `pnpm build` | 웹 production 빌드와 서버 번들 성공 |
| `pnpm test:e2e` | 빌드된 정적 웹·실행 중인 API에서 **4개 통과** |
| 실제 기본 시연용 렌더 | 같은 PC의 독립 브라우저 컨텍스트 3개, 256타일 완료, 승인 타일 85 / 91 / 80 |
| 1440px 데스크톱 / 390px 모바일 | 실제 화면 시각 점검, 모바일 가로 넘침·브라우저 오류 없음 |

추가 E2E는 프리셋 전환, 기본 8,000회·최대 20,000회 입력, 동의 전 Worker 미생성, 실제 Worker의 20,000회 계산과 전체 기준 픽셀 일치, 모바일 배치, 클립보드 API가 없는 환경에서 수동 복사 링크 표시를 확인한다. 이 테스트의 이미지는 CI 연산량을 제한하도록 128×128로 줄였다. 기존 참여 철회·이탈 재배정·취소·PNG·단독 결과 일치 검사는 그대로 통과했다.

별도 실제 브라우저 실행에서는 기본 시연 설정 전체 `2048×2048 / 8,000회`를 계산했다. 시작 버튼 클릭 직전부터 완료 및 PNG 활성화 확인까지 약 **14.1초**였으며, UI의 최종 합성 기준 시간은 **13.9초**였다. 같은 물리적 PC의 브라우저 3개에서 얻은 한 번의 관찰값으로, 서로 다른 기기 3대의 가속률을 의미하지 않는다. 완료 화면은 `docs/assets/distributed-render.png`에 갱신했다.

반복 상한을 높여도 이미지·타일 메모리 한도는 그대로다. 최대 반복 20,000회 입력 허용, 초과 입력 거절, 최대 설정의 메모리 제한과 청크 단위 취소도 테스트했다. 부하 증가는 실제 픽셀 해상도·반복 한도 변경으로 구현했으며 지연이나 가짜 진행률은 추가하지 않았다.

## 3D 영상 엣지 렌더팜 검증 (2026-10-11)

기본 홈페이지를 3D 애니메이션 렌더팜으로 전환하고 기존 프랙털을 `/fractal`에 보존했다. 브라우저가 CPU로 프레임을 렌더링하며 서버는 표본 검증·파일 저장·최종 MP4 인코딩만 담당한다.

| 검증 | 실제 결과 |
| --- | --- |
| `pnpm install --frozen-lockfile` | 성공, lockfile 일치 및 FFmpeg 실행 파일 설치 |
| `pnpm lint` | ESLint 및 전체 TypeScript 검사 통과 |
| `pnpm test` | **139개 / 7개 파일 통과** |
| `pnpm build` | 웹 production 빌드 및 서버 번들 성공 |
| `pnpm test:e2e` | **8개 통과**: 신규 영상 4개 + 기존 프랙털 4개 |
| 전체 기본 영상 렌더 | 1280×720, 120프레임, 24fps, 8샘플, 3회 반사 완료 |
| 최종 영상 | H.264 MP4, **1280×720·5.0초**, 305,477바이트, 재생·다운로드 확인 |
| 실제 기여도 | 같은 PC의 독립 Chromium 컨텍스트 3개가 각각 **40프레임** 계산, 재시도 0 |
| 1440px / 390px 화면 | 실제 화면 점검, 모바일 가로 넘침·페이지 오류 없음 |
| `docker build -t tabcloud:mvp .` | 새 의존성을 포함한 Linux 이미지 빌드 성공 |
| Docker FFmpeg smoke | 네트워크 없는 일회성 컨테이너의 uid1000에서 H.264 3프레임 파일 실제 생성 성공 |

139개 구성은 기존 테스트85개에 영상 설정17개, CPU 렌더러28개, 영상 서버9개를 추가한 것이다. 영상 서버 테스트는 인증·역할·결과 길이·표본 픽셀·중복·만료·재배정·디스크 저장 중 취소·인코더 실패·업로드 본문 중단·인코더 종료 후 디렉터리 삭제를 검증한다. FFmpeg의 실제 출력 파일도 디코딩하여 해상도와 프레임 수를 확인했다. 순서가 늦게 도착한 행 진행 보고는 무시하며 lease를 연장하지 않는 것도 확인했다.

신규 브라우저 E2E는 다음을 확인한다.

1. 독립 컨텍스트 3개가 동의 이후에만 실제 Worker를 실행하고, 각 프레임 업로드의 전체 RGBA가 기준 CPU 렌더와 일치한다. MP4의 해상도·길이·재생 시각 증가·다운로드 헤더를 검사한다. 첫 업로드429 재시도와 클립보드 없는 환경의 수동 초대도 확인한다.
2. 참여 중단 및 탭 종료 후 미완료 프레임을 다른 기기가 새 attempt로 계산한다. 관찰만 하는 방장은 Worker를 실행하지 않는다.
3. 방장 취소 후 Worker가 종료되고 미완성 영상은 다운로드할 수 없다.
4. 지연된 이전 상태 응답이 새 작업을 덮어쓰지 않고, 지연된 동의 응답도 연결 종료 뒤 CPU를 다시 켜지 않는다.

별도의 전체 720p 실행에서는 서버 기준 렌더 **166.957초**, 인코딩 **1.947초**, 전체 **168.904초**였다. 브라우저 자동화의 시작 클릭 직전부터 다운로드 활성화까지는 **169.262초**였다. 이는 기능 검증 중 얻은 한 번의 관찰값으로, 같은 PC에서 일부 린트·테스트·빌드가 함께 실행되었으므로 독립적인 성능 벤치마크나 물리적 3기기 가속률로 해석하지 않는다.

완성 영상은 [720p MP4](assets/tabcloud-720p-demo.mp4), 실제 설정·기여도·시간은 [실행 기록](assets/animation-measurements.json), 렌더링 중 화면은 [스크린샷](assets/animation-render.png)에 보존했다. 새 Docker 이미지에서는 FFmpeg 실행과 인코딩을 확인했고, 전체 브라우저 E2E는 로컬의 빌드된 웹·API에서 실행했다. 실제 서로 다른 기기와 공개 HTTPS 배포는 별도 시연 범위다.

## Vercel 분리 배포 지원 검증

2026-10-11, 웹의 `VITE_API_ORIGIN` 및 서버의 정확한 origin CORS 허용 기능을 추가한 뒤 다음을 실행했다.

- `pnpm lint`, `pnpm build` 통과.
- `pnpm test`: 167개 통과. 서버 CORS 6개 및 웹 URL 검증 22개를 추가했다.
- `pnpm test:e2e`: 영상·프랙털 기존 8개 전부 통과(1.1분).
- 별도 임시 프런트엔드 `127.0.0.1:5174`와 API `127.0.0.1:13031`에서 실제 Chromium 컨텍스트 2개로 분리 출처 smoke 실행. 320×180, 24프레임을 각 12개씩 계산했으며 1초 MP4(21,159바이트) 생성·재생·다운로드 성공. API 123건이 별도 서버로 전달되고 미리보기·영상·업로드의 CORS, 프런트엔드 origin의 초대 링크 및 별도 서버의 프랙털 WebSocket 연결을 확인했다. JavaScript 오류는 없었다. 테스트용 서버는 모두 종료했다.
- Vercel 빌드 가드가 미설정 서버 주소 및 HTTP 서버 주소를 거부하는 것을 확인했다. 실제 배포는 HTTPS 서버 상태 확인을 통과해야 진행된다.

위 결과는 로컬 기능 검증이다. 공개 URL에서의 최종 검증과 호스팅 계정의 실제 배포 상태를 대신하지 않는다.

Render 절전 복귀에 대응하는 GET readiness 대기·재시도·취소 13개 테스트를 추가한 후 `pnpm test`는 **180개** 통과했다. ESLint·TypeScript·프로덕션 빌드도 재검증했다. 변경된 분리 출처 브라우저 smoke에서도 24프레임과 MP4 재생·다운로드·WebSocket 연결을 확인했다(각 12프레임, JavaScript 오류 없음). `.vercelignore` 적용 후 배포 dry run의 파일 목록에 `.env*`, `.qa`, `.vercel`, 의존성 및 빌드 산출물이 없는 것을 검사했다. Render의 Blueprint API 검증은 `valid: true`이며 서버의 실제 HTTPS `/healthz` 응답과 정확한 CORS 헤더도 확인했다.


## CPU·RAM·GPU 자원 한도 검증 (2026-10-11)

영상 스튜디오에 기기별 자원 설정과 CPU/WebGPU 공용 행 작업 큐를 추가했다. CPU Worker 수와 휴식 비율, GPU 제출·읽기·보정 시간을 포함한 휴식 비율, 렌더링 버퍼 예산으로 한도를 적용한다. OS 전체 사용률 또는 전체 브라우저 메모리 제한을 보장하지 않는다.

- `pnpm lint`: ESLint 및 전체 TypeScript 통과.
- `pnpm test`: **216개 / 11개 파일 통과**. 행 분할 참조 픽셀 일치·최종 청크를 포함한 시간 예산·취소·RAM 부족·0%·CPU/GPU 공유 큐·GPU 실패 시 허용된 CPU만 사용하는 대체 동작을 검증했다.
- 프로덕션 웹·서버 빌드 성공.
- `REQUIRE_WEBGPU=1`을 설정한 `pnpm test:e2e`: **14개 모두 통과, 생략 0개**. 기존 영상·프랙털 8개, 자원 설정 3개, GPU 3개다.
- 실제 **NVIDIA GeForce RTX 3060 Ti**에서 Chromium의 WebGPU 어댑터 `ampere`, 소프트웨어 대체 아님을 확인했다. GPU 테스트는 full Chromium의 새 headless 모드를 사용한다.
- CPU 0%·GPU 50% 및 CPU 25%·GPU 50% 각각 320×180·4프레임·8샘플을 실제 계산했다. 기존 서버 표본 검증을 통과하고 MP4 생성·재생·다운로드까지 완료했다. CPU 0% 실행은 CPU 자식 Worker를 만들지 않았다. GPU 정밀도 보정에는 여전히 CPU가 사용된다.
- 별도 720p 전체 픽셀 비교 4건(0·57번 프레임, 8샘플·3반사 및 32샘플·4반사)은 CPU 참조 대비 모든 채널 오차 ≤1이었다. 서버 검증 허용 오차는 확대하지 않았다. 수치 경계 픽셀의 약 8~17%를 CPU로 보정했다.
- CPU·GPU 0%, RAM 0% 참여 차단, 브라우저 설정 저장·별도 프로필 독립성, 설정 변경 시 실제 연산 즉시 정지·동의 철회·재동의 후 완료를 확인했다. GPU 실행 중 0% 변경도 검증했다.
- 늦은 참여 응답과 후속 철회 응답이 새 연산을 재시작하거나 새 참여를 취소하지 않도록 대기하며 회귀 테스트했다. 새로고침 재접속 후 남던 인증 오류 안내도 수정했다.
- 영상의 별도 최대 시도 시간 10분을 검증했다. 실제 진행이 있는 130초 시도는 허용하고, 진행을 계속 보고해도 10분에는 재배정한다. 기존 프랙털 한도 120초는 유지한다.
- 390px 모바일 화면 가로 넘침 없음, JavaScript 오류 없음.

[GPU 실행과 720p 픽셀 비교 기록](assets/resource-validation.json)에 설정·연산 시간·MP4 크기를 저장했다. 시간은 동일 PC의 기능 테스트 중 관찰값이며 다른 기기 사이의 성능 비교나 OS CPU/GPU 사용률 실측값이 아니다. GPU 미지원 환경의 일반 CI는 GPU 테스트를 생략할 수 있으며, 위 로컬 실행은 GPU를 필수로 요구해 실제 연산을 검증했다.
