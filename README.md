# TabCloud — 브라우저 엣지 렌더팜

**사용자가 업로드한 영상**의 프레임을 여러 브라우저에 나누어 **노이즈 제거·선명도·색 보정**을 처리합니다. 실제 하드웨어 **WebGPU compute shader**와 **CPU Web Workers**가 계산하고, 서버가 완성된 프레임과 원본 오디오를 MP4로 묶습니다. 각 참여자는 CPU·GPU 연산 한도와 RAM 작업 예산을 정하고 **연산 참여**를 눌러야 계산합니다. GPU 장치와 실제 처리 프레임·dispatch 실적을 화면에서 확인할 수 있습니다.

메인 화면(`/`)은 업로드 영상 작업실입니다. 기존 3D 레이트레이싱 데모는 `/animation`, 프랙털 데모는 `/fractal`에 유지했습니다. 업로드 작업의 구조와 제한은 [업로드 영상 처리 가이드](docs/VIDEO.md)에 있습니다.

[TabCloud 웹](https://tabcloud-silk.vercel.app) · [서버 상태](https://tabcloud-api.onrender.com/healthz)

웹은 Vercel, 렌더링 서버는 Render Free를 사용합니다. 한동안 접속하지 않았으면 서버를 깨우는 데 약 1분이 걸릴 수 있습니다. 방 생성 전 최대 90초 동안 연결을 기다립니다. 서버 재시작·절전 시 방과 결과가 초기화되는 시연용 배포입니다.

기존 데모 기록: [3D 영상 예시](docs/assets/tabcloud-720p-demo.mp4) · [동일 PC의 브라우저 3개 실행 기록](docs/assets/animation-measurements.json). 이 기록은 업로드 영상 필터 성능과 별개입니다.

## 빠른 시작

Node.js 24 LTS 권장(최소 22.13), pnpm 9.15.9, 최신 브라우저가 필요합니다. Windows에서는 설치된 `ffmpeg-static`을 기본 사용하며, Linux에서는 시스템 FFmpeg를 설치하고 `FFMPEG_PATH=/usr/bin/ffmpeg`를 지정합니다. Docker 이미지는 FFmpeg를 포함합니다. 영상 프레임용 임시 디스크 공간도 필요합니다. Docker 실행에는 Docker Engine/Desktop 및 Compose 2.24 이상이 필요합니다.

```sh
npm install --global pnpm@9.15.9
pnpm install --frozen-lockfile
pnpm dev
```

브라우저에서 **http://localhost:5173**에 접속하세요. Vite 웹과 Fastify API(기본 3001)가 함께 시작되며, `/api`, `/ws`, `/healthz`는 개발 프록시를 사용합니다. 개발 서버에서도 요청의 원래 Host를 보존해 출처 검사를 통과합니다. 서버 설정을 바꾸려면 `.env.example`을 `.env`로 복사하세요(PowerShell: `Copy-Item .env.example .env`, macOS/Linux: `cp .env.example .env`). `.env`가 없어도 기본값으로 실행됩니다.

프로덕션 빌드는 동일한 출처에서 웹·API·WebSocket을 제공합니다.

```sh
pnpm build
pnpm start
```

접속 주소: **http://localhost:3001**. 상태 확인: `/healthz`.

## 사용 순서

1. **방 만들기**를 누르고 영상을 업로드합니다. 파일당 최대 **256 MiB·2분**, MP4·MOV·WebM·MKV·AVI·TS 등 여러 형식을 받습니다. 세로 영상도 원본 비율을 유지합니다.
2. 출력 해상도(720p/1080p), 프레임률(원본/24/30/60fps), 화질과 보정값을 정합니다. 기본값은 **1080p·원본 프레임률(최대 60fps)·고화질**이며 원본보다 확대하지 않습니다. 초대 링크로 연결한 참여 기기에 영상 프레임이 전송됩니다.
3. 각 기기에서 자원 한도를 정하고 **연산 참여**를 누릅니다. 업로드 모드 기본값은 CPU 25%, GPU 100%, RAM 10%입니다. GPU를 지원하지 않는 환경은 화면에 표시하며 허용한 CPU 한도만 사용합니다.
4. 방장이 **처리 시작**을 누르면 참여 기기가 프레임을 가져갑니다. 빠른 기기는 다음 프레임을 먼저 요청하므로 더 많은 일을 맡습니다. GPU 장치·실제 처리 실적과 기기별 완료 프레임을 확인합니다.
5. 완료 영상을 재생하거나 **영상 다운로드**를 누릅니다. 오디오가 있으면 유지합니다. **연산 중단**은 해당 기기를, **작업 취소**는 전체 작업을 중단합니다. 같은 원본에 다른 보정값을 적용할 수도 있습니다.

자원 비율이나 출력 설정을 바꾸면 참여를 철회합니다. 새 한도로 시작하려면 **연산 참여**를 다시 누릅니다. GPU를 사용할 수 없어도 설정한 CPU 한도를 자동으로 높이지 않습니다.

동일 컴퓨터에서는 시크릿 창이나 별도 브라우저 프로필을 사용하면 역할이 확실히 분리됩니다. 물리적 기기에서 테스트하려면 `localhost` 대신 서버의 LAN 주소로 처음부터 접속해 방을 만드세요. 예: `http://192.168.0.10:5173`. 일반 LAN HTTP에서는 CPU 모드를 사용합니다. WebGPU는 HTTPS 또는 `localhost`의 보안 컨텍스트와 지원 브라우저·어댑터가 필요합니다. 방화벽은 사용자가 허용한 사설 네트워크에서만 해당 포트를 개방하세요.

## 자원 한도의 의미

- CPU는 브라우저가 보고한 논리 코어 수에 비율을 곱해 Worker 수와 연산·휴식 시간을 정합니다. Worker는 최대 16개이며 RAM 예산에 따라 더 줄어듭니다. 예를 들어 12개 논리 코어의 25%는 Worker 3개, 5%는 Worker 1개를 약 60%의 연산 시간 비율로 실행합니다.
- RAM은 브라우저가 제공하는 대략적인 기기 용량에 대한 **렌더링 버퍼 예산**입니다. 용량을 알 수 없으면 512 MiB를 기준으로 삼고, 최종 예산은 최대 512 MiB입니다. 프레임·업로드·구간 버퍼와 Worker 여유분을 계획에 포함하며, 비율을 채우려고 불필요한 메모리를 할당하지 않습니다. 브라우저·드라이버 전체 메모리나 OS의 RSS 제한은 아닙니다.
- GPU는 실제 WebGPU 연산 후 처리·읽기 시간에 비례해 쉽니다. GPU 0%에서는 GPU 장치를 만들거나 계산을 제출하지 않습니다. 새 업로드 필터는 정수 계산을 사용해 CPU 픽셀 보정 없이 동일한 결과를 냅니다. 소프트웨어 GPU를 하드웨어 GPU로 사용하지 않으며, 지원하지 않으면 허용된 CPU 한도 안에서 처리합니다. CPU 0%도 GPU 제어·전송·브라우저 자체의 CPU 사용까지 없애지는 않습니다.

이 비율은 시스템 사용률을 정확히 고정하거나 자원을 반드시 그만큼 소모하게 하는 기능이 아닙니다. CPU·GPU 연산 시간을 제한하고 RAM 예약을 관리합니다. 같은 기기의 여러 탭에서 실행하면 각 탭의 사용량이 합산됩니다. 이 설정은 영상 모드에 적용하며 기존 프랙털 모드는 Worker 1개 정책을 유지합니다. 세부 계산과 제약은 [영상 렌더팜 가이드](docs/ANIMATION.md#기기별-cpuramgpu-설정)를 참고하세요.

## 구현 범위

업로드 처리의 자세한 구조는 [영상 처리 가이드](docs/VIDEO.md), 기존 3D 데모는 [렌더팜 가이드](docs/ANIMATION.md)에 있습니다.

- 최대 256 MiB·2분 영상 업로드, 세로/가로 1080p·최대 60fps, 출력 화질 선택
- 24프레임 단위 디코딩·분산 처리·인코딩·중간 파일 정리, 무손실 gzip 프레임 전송
- WebGPU 정수 셰이더와 CPU Worker의 노이즈 제거·선명도·색 보정
- 실제 GPU 어댑터·처리 프레임·dispatch 횟수, 지원 시 GPU timestamp 측정
- 참여 동의·활성 lease가 있는 기기에만 해당 원본 프레임 전달
- CPU/GPU 동일 픽셀 계산과 서버 표본 검산, 원본 오디오를 포함한 MP4 조립

기존 3D 데모의 구현 범위:

- CPU·WebGPU 3D 레이트레이싱: 금속 구체, 바닥 반사, 움직이는 카메라·조명·물체, 샘플링
- 기기별 CPU·GPU 연산 한도와 RAM 예산, 빠른 기기·연산 장치가 다음 작업을 가져가는 자동 분배
- 독립 프레임 분배, 명시적 참여·즉시 중단, heartbeat·lease·재시도·중복 거절
- 프레임별 바이너리 업로드·표본 재검산·PPM 디스크 저장, 작은 PNG 미리보기
- 서버의 제한된 FFmpeg 인코딩, H.264 MP4 재생·다운로드, 취소·만료 시 파일 정리
- 720p·최대 240프레임·32샘플·4회 반사, 브라우저당 활성 프레임 1개·CPU Worker 최대 16개·GPU 구간 1개

기존 프랙털 모드(`/fractal`)도 다음 기능과 함께 유지합니다.

- 추측하기 어려운 방 ID·초대 토큰, 별도 방장 토큰, 만료·가명 참가자·실시간 상태
- 결정적 Mandelbrot 엔진, 부분 경계 타일, 실제 Worker 1개/브라우저, Canvas 합성과 PNG
- 명시적 참여·즉시 중단, pull 방식 작업 배정, heartbeat·진행 보고·lease·attempt ID
- 이탈·타임아웃 재배정, 중복·오래된 결과 거절, 재시도 한도와 실패·취소 상태
- 타일당 최대 8개 픽셀 서버 재검산, 버퍼 길이·입력 범위·권한·메시지 제한
- 완료 결과 재전송, 새로고침·재연결 후 재동의, 만료·서버 재시작 안내
- 같은 엔진의 단독 실행, 결과 체크섬 비교, 완료 시간·기여도·검증 시간·전송량 계측
- 반응형 한국어 UI, Docker, Vitest, Playwright, GitHub Actions

## 검증 명령

```sh
pnpm lint
pnpm test
pnpm build
pnpm exec playwright install chromium
pnpm test:e2e
```

`pnpm lint`는 ESLint와 전체 TypeScript 검사를 수행합니다. `pnpm test`는 계산·스키마·실제 로컬 WebSocket 서버 통합 테스트를 실행합니다. `pnpm test:e2e`는 **먼저 빌드한** 정적 앱을 사용하며, 필요하면 서버를 자동으로 실행합니다. 실패 시 `playwright-report/` 및 `test-results/`에 trace·스크린샷을 저장합니다. `pnpm check`로 전체 검증을 순서대로 실행할 수 있습니다. CI도 같은 흐름과 Docker 빌드를 실행하도록 구성했습니다.

E2E는 방장과 참여자 두 명의 독립 컨텍스트에서 실제 Worker 실행·각 기여도·전체 픽셀 일치·MP4 재생과 다운로드·동의·중단·이탈 복구·취소를 확인합니다. 자원 설정 저장·0% 차단·변경 시 중단과 지연된 동의 응답도 검증하며, 기존 프랙털의 PNG·단독 측정 검증을 유지합니다. **동일 머신의 컨텍스트 테스트는 물리적 기기 3대의 성능 실험이 아닙니다.** 실제 실행한 명령과 결과는 [검증 기록](docs/VALIDATION.md)에 있습니다. GitHub 원격 CI 실행은 이 로컬 검증과 별개입니다.

WebGPU 테스트는 전체 Chromium의 새 headless 모드에서 실제 어댑터로 렌더링하고 CPU 기준 픽셀과 채널당 오차 1 이내인지 확인합니다. GPU 전용·CPU 혼합 렌더링의 서버 업로드와 MP4도 검증합니다. 기본 CI에서 어댑터가 없으면 해당 테스트를 건너뜁니다. `REQUIRE_WEBGPU=1`로 실행하면 어댑터가 없을 때 실패합니다. 이 옵션 자체가 소프트웨어 어댑터를 제외하지는 않으며 실제 어댑터 이름과 대체 어댑터 여부를 기록합니다.

```powershell
$env:REQUIRE_WEBGPU = '1'
pnpm exec playwright test tests/e2e/gpu.spec.ts tests/e2e/gpu-integration.spec.ts
Remove-Item Env:REQUIRE_WEBGPU
```

이미 실행한 로컬 테스트 컨테이너를 검증하려면 `E2E_BASE_URL=http://127.0.0.1:3003` 환경변수를 설정한 뒤 `pnpm test:e2e`를 실행할 수 있습니다. 이 경우 테스트는 서버를 따로 시작하지 않으며 해당 서버에 임시 방과 연산을 생성합니다.

## Docker

Vercel에 웹 화면을 배포할 때는 렌더링 서버를 별도 단일 인스턴스에 연결합니다. [Vercel + Render 배포 절차](docs/DEPLOYMENT.md#vercel--render)를 참고하세요. 루트의 `vercel.json`과 `render.yaml`에 설정을 준비했습니다.

```sh
docker compose up --build -d
docker compose logs -f tabcloud
docker compose down
```

접속 주소는 **http://localhost:3001**입니다. `.env`가 있으면 운영 제한을 컨테이너에 전달합니다. Compose의 `PORT`는 외부 포트이고 컨테이너 내부는 항상 3001입니다. HTTPS 배포에서는 `PUBLIC_ORIGIN=https://실제도메인`을 설정하고 TLS 리버스 프록시를 사용하세요. 자세한 명령과 Caddy 예시는 [배포 가이드](docs/DEPLOYMENT.md)에 있습니다.

## 프랙털 모드 운영 기본값과 제한

영상 모드는 [별도의 디스크·프레임 제한과 처리 흐름](docs/ANIMATION.md)을 사용합니다. 아래 표는 기존 프랙털 모드의 값입니다.

| 항목 | 기본값 |
| --- | --- |
| 이미지/연산 | 64..2048px 각 변, 최대 4,194,304픽셀, 10..20000회 반복 |
| 타일/브라우저 | 32·64·128px, 최대 4096타일, Worker/활성 lease 각 1개 |
| 방/참가자 | 서버 32방, 방당 연결 24명, 참여 기록 64명 |
| 방 보존 | 생성 후 1시간, 빈 방 10분 후 정리 |
| 연결/작업 시간 | heartbeat 20초, lease 15초, attempt 최대 120초, 작업 10분 |
| 재시도 | 최초 시도 외 5회 재시도; 초과 시 전체 작업 실패 |
| 메시지 | 96KiB, 연결당 초당 250개, 방 생성 IP당 분당 10개 |
| 저장 예산 | 작업당 24MiB, 서버 전체 128MiB 예약, 송신 대기 2MiB |

실제 Worker의 증가하는 행 진행 보고만 lease를 연장합니다. heartbeat는 연결 확인용으로 계산 완료를 대신하지 않습니다. 최대 attempt 시간 이후에는 재배정합니다. 결과는 다음 작업·방 만료·빈 방 정리까지 보관해 다운로드와 재접속을 지원합니다. 한도 내 입력도 조합과 서버 잔여 예산에 따라 거절될 수 있습니다. 예를 들어 2048²/32px 타일은 기본 작업 메모리 예산을 넘으므로 64px 이상 타일을 사용하세요. 메모리 예산은 결과와 메타데이터의 예약치로 Node 프로세스 전체 RSS 제한과 동일하지 않습니다.

프랙털 시연용은 기존 1024²/500회보다 픽셀 수가 4배, 반복 상한이 16배입니다. 이는 최대 연산 예산 비교이며 실제 소요 시간이 64배라는 의미는 아닙니다. **최대 부하**는 2048²/20,000회, **가볍게**는 1024²/500회입니다. 프랙털의 모든 프리셋은 Worker 1개와 명시적 참여·중단 정책을 유지합니다. 상세 로그는 **활동 기록**, 체크섬·계측 설명은 **측정 정보**에서 펼쳐 볼 수 있습니다. 영상 모드의 연산 한도에는 의도적인 휴식 시간이 포함됩니다.

## 정확성·신뢰·개인정보

실행할 코드는 내장 영상 필터·3D 장면·Mandelbrot 엔진으로 고정되어 있습니다. 사용자 영상 파일만 업로드하며 임의 코드·FFmpeg 명령·카메라·마이크·계정 기능은 없습니다. 원본은 서버의 임시 저장소에서 디코딩되고, 프레임은 동의한 참여 기기로 전달됩니다. 초대 링크를 받은 사람에게 원본 내용과 처리 결과가 공유되는 작업입니다. 초대 토큰은 URL fragment에, 방장 토큰은 해당 탭의 `sessionStorage`에 저장합니다. 방장 토큰은 초대 링크에 포함하지 않습니다. 동일 탭 새로고침 시 유지되지만 닫으면 관리 권한 복구를 보장하지 않습니다. 탭 복제 시 브라우저가 세션 저장소를 복사할 수 있으므로 방장 탭 자체를 타인에게 넘기지 마세요.

브라우저는 신뢰할 수 없는 노드입니다. 표본 검증은 일반 오류 탐지이며 악의적인 결과의 전체 무결성을 보장하지 않습니다. UI FNV-1a 체크섬은 비교용이며 암호학적 증명이 아닙니다. 자동화는 CPU 렌더의 전체 RGBA 바이트 일치와 GPU 렌더의 채널당 허용 오차를 검증합니다. HTTP 서버 로그에는 IP·경로 등 운영 정보가 남을 수 있고, 프록시 로그 보존은 운영자가 정합니다.

공개 배포에는 HTTPS/WSS가 필요합니다. 서버는 origin 검사, 보안 헤더, 입력·권한·빈도·메모리 제한을 적용합니다. API의 IP 제한은 기본적으로 프록시를 신뢰하지 않으므로 역방향 프록시 뒤에서는 프록시 IP를 함께 제한할 수 있습니다. 외부 공개 서비스의 인증·참가자 차단·DDoS 방어·영속 저장·다중 서버 운영은 MVP 범위 밖입니다.

서버 재시작 시 모든 방과 결과가 사라집니다. 브라우저마다 Worker 실행과 백그라운드 타이머 정책이 다르며 숨김·절전 시 느려지거나 lease가 만료될 수 있습니다. 정확한 CPU 사용률은 강제하지 않습니다. 자동 브라우저 검증은 Chromium에서 수행했으며 Safari·Firefox의 모든 버전을 검증한 것은 아닙니다.

## 시간 측정의 의미

영상 모드는 서버의 렌더·인코딩·전체 시간을 구분합니다. 전체 시간은 시작부터 MP4 파일 완성까지이며, 브라우저 다운로드·재생 시간은 포함하지 않습니다. 아래의 단독 측정 버튼과 체크섬 비교 설명은 프랙털 모드에 해당합니다.

분산 비교 시간은 방장 브라우저에서 **시작 클릭→전체 타일 합성 후 화면 프레임**을 `performance.now()`로 측정합니다. 새로고침·재연결 시 이 기준값은 폐기하며 속도 비율을 만들지 않습니다. 서버의 **시작→전체 결과 승인** 시간도 따로 표시합니다. 단독 실행은 같은 설정과 Worker 1개로 초기화·계산·캔버스 합성을 포함합니다. 작업 완료 후 비교하므로 다른 분산 작업과 CPU를 중복 점유하지 않습니다.

`단독 시간 / 분산 시간`은 실측값이 모두 있을 때만 표시합니다. 할당→결과 수신 시간 합계는 여러 기기에서 겹치고 계산·대기 시간을 포함하므로 순수 통신 오버헤드가 아닙니다. Worker 시간은 클라이언트 보고값이며 행 단위 양보 시간도 포함합니다. 작은 작업은 분산 쪽이 더 느릴 수 있습니다. 성능 향상 수치는 보장하지 않습니다.
